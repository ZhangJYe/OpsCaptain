# 第1章：项目概览

> **目标：** 30 分钟建立全局地图。学完这章，你能用一句话讲清楚 OpsCaption 是什么、用了什么技术、整体架构长什么样。

---

## 1. 一句话概括

> **OpsCaption 是一个用 Go 语言写的智能运维助手。运维人员用自然语言描述故障，系统自动查指标、查日志、查知识库，整合成带证据的诊断报告。**

用人话：你在 Slack / 飞书 / Web 上 @机器人 说 "checkoutservice CPU 告警了怎么办"，它自动帮你去 Prometheus 查指标、去日志平台查错误日志、去知识库查 SOP 文档，最后让 LLM 综合这些信息给出诊断建议——你不需要在四五个系统之间来回切。

---

## 2. 解决的问题

### 痛点：运维的"多窗口地狱"

```mermaid
graph TD
    A[收到告警] --> B[打开 Prometheus 看指标]
    B --> C[打开日志平台搜日志]
    C --> D[打开 Confluence/语雀 查 Runbook]
    D --> E[打开飞书/钉钉 问同事]
    E --> F[自己脑子里拼凑信息]
    F --> G[写诊断结论]

    style A fill:#ff6b6b,stroke:#333,color:#fff
    style G fill:#51cf66,stroke:#333,color:#fff
```

**问题：**
- 来回切换 4+ 个系统，信息分散
- 新人不知道查什么、去哪查
- 凌晨 3 点被叫醒，脑子不清醒，容易漏步骤

### OpsCaption 怎么做

```mermaid
graph TD
    A["你（自然语言）说：checkoutservice CPU 告警了怎么办？"] --> B[OpsCaption]

    subgraph B[OpsCaption]
        B1[🔍 自动查 Prometheus 指标]
        B2[🔍 自动查日志平台]
        B3[🔍 自动查知识库 SOP]
        B4[🧠 LLM 综合 → 诊断报告]
    end

    B --> C[诊断报告（带证据引用）]

    style A fill:#4dabf7,stroke:#333,color:#fff
    style C fill:#51cf66,stroke:#333,color:#fff
```

**诊断报告示例：**
> "根据 Prometheus 数据显示 CPU 使用率 87%，接近 limit 2.0 核；
> 日志中出现 12 次 context deadline exceeded；
> 建议：1) 调高 resource limits 到 3.0 核 2) 检查下游服务超时配置"

**核心价值：** 把运维经验产品化——不是替代运维，而是让每个运维都像带着一个资深搭档。

## 3. 技术栈速记表（含 trade-off）

| 技术                          | 在项目里做什么                 | 为什么选它                                                                                                                                                                                     | 不选什么 & trade-off                                                                             |
| --------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Go 1.24**                 | 整个后端的编程语言               | 编译成单二进制（Docker 镜像 <20MB）、goroutine 天然并发、Agent 编排和工具调用不需要引入第二语言                                                                                                                            | **不选 Python**：Python 的 asyncio 写并行 tool calling 没有 Go context 包统一，部署镜像轻松过 1GB                |
| **GoFrame v2**              | HTTP 框架：路由、中间件、SSE      | 国产 Go 框架中文档最完整，自带配置/日志/缓存/校验，开箱即用                                                                                                                                                         | **不选 Gin**：更轻但需自己拼中间件生态，GoFrame 一体化节省配置成本                                                    |
| **Eino**                    | LLM 编排框架，构建 Agent 执行图   | 字节开源，Go-native，原生 ReAct 和 Plan-Execute-Replan 模式，ADK 理念提供完整 Agent 运行时                                                                                                                     | **不选 LangGraph**：生态更好但需引入 Python——多一套部署和依赖，个人项目太重                                            |
| **DeepSeek V4 Pro/Flash**   | 推理/Query Rewrite/Rerank | 兼容 OpenAI API 的国产大模型，推理能力强，中文能力优秀，价格有竞争力。当前配置用 `chat_model=deepseek-v4-pro`、`chat_model_fast=deepseek-v4-flash`；代码里的 `OpenAIForGLM` / `OpenAIForGLMFast` 是历史函数名，实际读取 OpenAI-compatible 配置 | **不选 GPT-4**：RAG 链路大量 LLM 调用，每次走 GPT-4 成本不可接受                                                |
| **Milvus**                  | 向量数据库，ANN 近似检索          | 开源标杆，Go SDK 官方维护，原生支持向量+标量过滤                                                                                                                                                              | **不选 Pinecone**：SaaS 需数据上云，内部运维文档有安全风险。**不选 Weaviate**：Go 客户端社区维护，API 覆盖不全                   |
| **Doubao Embedding Vision** | 文档→2048维向量              | 字节跳动的多模态 embedding 模型，支持文本和图片，中文技术文档效果优秀，通过火山引擎 API 调用                                                                                                                                    | **不选 BGE-M3**：需要额外部署，Doubao 是字节原生服务，与 Eino 框架同生态                                             |
| **RabbitMQ**                | 消息队列：异步任务+记忆抽取          | 消息级 ACK、TTL+DLX 天然支持延迟重试、单节点部署无 ZK 依赖                                                                                                                                                     | **不选 Kafka**：适合高吞吐日志流，我的场景是任务队列——RabbitMQ 的任务语义更匹配。Kafka 最小部署吃 2GB+ 内存                       |
| **Redis**                   | 缓存+会话状态+限流计数+任务状态机      | 内存级速度，SETNX 做幂等，过期策略做自动清理                                                                                                                                                                 | 无——后端标配                                                                                      |
| **Prometheus**              | 指标采集和监控                 | 云原生监控事实标准，Go 生态完美集成                                                                                                                                                                       | 无                                                                                            |
| **OpenTelemetry**           | 分布式链路追踪                 | 行业标准 API，不锁厂商                                                                                                                                                                             | 无                                                                                            |
| **Docker**                  | 容器化部署                   | 环境一致，部署简单                                                                                                                                                                                 | 无                                                                                            |
| **React + TypeScript**      | 前端 SPA（20组件）            | Framer Motion 动画、暗色模式、打字机流式渲染、SkillPanel 可视化开关、AIOpsPanel 三路证据[[]]诊断卡片                                                                                                                    | **不选原生 HTML/JS**：随着交互复杂度增长（技能面板、证据卡片、流式渲染），React 组件化 + 状态管理成为刚需——从原生 HTML 重构为 React 是刻意的架构升级 |

> 💡 **面试技巧：** 按三列回答——"做了什么 + 为什么选它 + 不选什么"。**说出 trade-off 是 Senior Engineer 的标志**，不要只说"我选了最好的技术"。

### 四层职责一句话总结

| 层 | 一句话 | 类比 |
|----|--------|------|
| **Controller** | "接待来访"——接收 HTTP 请求，返回 HTTP 响应 | 公司的前台 |
| **Service** | "后勤保障"——管理记忆、装配上下文、审批、降级 | 行政/后勤部门 |
| **Agent** | "思考执行"——接收问题，调用工具，生成回答 | 技术专家 |
| **Support** | "基础设施"——知识库、缓存、消息队列、监控 | 公司的水电网 |

> 💡 **面试时画架构图的口诀：** "四层架构，从上到下：接入层收请求，服务层做保障，Agent 层做推理，支撑层提供基础设施。数据流从 Controller 进 → Service 装配上下文 → Agent 推理执行 → 调用 Support 层工具 → 原路返回。"

1. **Controller 层**：接请求、取参数、返回响应
    只做入口处理：
    接收 /api/chat、/api/chat/stream、/api/ai_ops 等请求，**解析参数，调用对应 App，最后把结果转成 HTTP JSON 或 SSE****。它不直接查 DB、不直接调 Milvus、不直接跑 Agent。
    
2. **Application 层**：决定这次请求怎么跑
    以 Chat 为例，ChatApp 大概做这些事：
	1. 校验输入：问题不能为空、session id 合法、prompt injection 检查。
	2. 检查降级：比如 kill switch、依赖不可用时返回 degraded。
	3. 管理 session 锁：避免同一个 session 并发互相污染上下文。
	4. 调用 MemoryService / ContextEngine：构建 history、memory、docs 等上下文包。
	5. 构建并运行 ReAct Agent。
	6. 处理输出：保存记忆、记录 token audit、返回 answer / trace / sources。
3. **AI Domain 层**：真正做 Agent / RAG / Memory / 推理
    
    这是项目最核心的“业务大脑”，在 internal/ai/ 下面。
    里面包括：
    - ReAct Agent：普通聊天、知识问答、按需调用工具
    - Plan-Execute-Replan：复杂事故诊断，先规划、再执行、再复盘
    - ContextEngine：控制 history / memory / docs / tool results 怎么进上下文
    - MemoryService：长期记忆、短期上下文、记忆写回
    - RAG：Milvus + BM25 + RRF + RetrieveRefine
    - 防幻觉：SchemaGate、OutputValidator、Contract、LLMValidation
4. **Infrastructure 层**：连接 Milvus、MQ、文件系统等外部资源
    
    主要在 internal/infra/，负责外部系统适配，比如：
    
    - Milvus 向量库
    - RabbitMQ
    - 文件上传存储
    - 后续可扩展 Redis、Prometheus、MCP Server 等
    
    这一层的重点是“适配外部系统”，不放核心推理逻辑。

## 5. 一次请求的旅行

下面跟踪一条真实的用户请求，从 HTTP 请求进来到响应返回的完整路径。

假设用户问了：**"checkoutservice CPU 告警了怎么办？"**

```mermaid
sequenceDiagram
    participant U as 👤 用户浏览器
    participant C as 第1层 Controller
    participant S as 第2层 Service
    participant A as 第3层 ReAct Agent
    participant P as 第4层 Support

    U->>C: POST /api/chat<br/>{"query": "checkoutservice CPU 告警了怎么办？"}
    Note over C: 0ms - Auth 认证 → RateLimit 限流

    C->>S: 10ms - 传递请求
    Note over S: ① MemoryService: 检索用户历史记忆<br/>② ContextAssembler: 装配上下文<br/>③ 设置 ContextBudget

    S->>A: 50ms - 装配好的上下文
    Note over A: Think（第1轮）:<br/>"需要查指标、日志、知识库"

    A->>P: 80ms - 调用工具
    Note over P: query_metrics → Prometheus API<br/>"CPU 使用率 87%，limit 2.0 核"<br/>query_logs → 日志平台<br/>"12 条 context deadline exceeded"<br/>query_docs → Milvus RAG<br/>"SOP-042: CPU 高负载处理指南"

    P->>A: 200ms - 工具结果返回
    Note over A: Observe: 分析结果<br/>Think（第2轮）:<br/>"综合证据，判断资源不足"

    A->>S: 500ms - 生成最终回答
    Note over S: MemoryService.PersistOutcome<br/>TokenAudit: 记录 token 消耗

    S->>C: 520ms - 返回响应
    C->>U: HTTP Response<br/>{"answer": "根据分析...", "sources": [...]}
```

### 这条路径的关键信息

| 环节 | 谁在做 | 做了什么 |
|------|--------|---------|
| 接入 | Controller（GoFrame） | 认证、限流、解析请求 |
| 准备 | Service | 加载记忆、装配上下文、设定预算 |
| 推理 | ReAct / Plan-Execute-Replan（Eino） | 简单查询走 ReAct，复杂故障走 Plan-Execute-Replan |
| 数据 | Support | 查 Prometheus、查日志、查 Milvus 知识库 |
| 收尾 | Service | 保存记忆、审计 token |

## 6. 面试问答

### Q: "介绍一下你的项目"

#### 🎯 30 秒版（面试开场自我介绍）

> "我独立开发了一个叫 OpsCaption 的智能运维助手，用 Go 语言写的。核心功能是：运维人员用自然语言描述故障，系统自动去查 Prometheus 指标、查日志、查知识库，然后由 LLM 综合这些信息生成带证据引用的诊断报告。
>
> 技术栈是 Go + GoFrame + 字节的 Eino 编排框架 + DeepSeek V4 大模型 + Milvus 向量数据库。Agent 层有两条主链路：普通问答走 ReAct，事故诊断走 Plan-Execute-Replan；复杂根因假设收敛可以启用 GoS（BeliefGraph + FSM）。我还做了上下文压缩、防幻觉管线、多层安全防护等生产级工程。"

#### 🎯 2 分钟版（面试官追问"展开说说"）

> "好的，我从三个维度展开。
>
> **第一，为什么做这个项目。** 运维团队日常排障要在 Prometheus、日志平台、知识库、飞书之间来回切，信息分散，新人上手慢。我就想做一个统一入口，用自然语言驱动排障流程。
>
> **第二，技术架构。** 整体是四层：
> - Controller 层用 GoFrame 做 HTTP 服务，支持同步聊天、SSE 流式响应和异步任务；
> - Service 层负责记忆管理、上下文装配、降级和审批；
> - Agent 层是核心，基于 Eino 框架实现两条主链路：简单查询用 ReAct Agent，复杂故障排查用 Plan-Execute-Replan。还有信念图（BeliefGraph + FSM）驱动的 GoS 诊断引擎；
> - Support 层提供基础设施：Milvus 向量库做 RAG 检索，Redis 做缓存，RabbitMQ 做异步任务，Prometheus + Jaeger 做可观测性。
>
> **第三，生产级工程。** 我做了很多确保系统可靠运行的工程：上下文压缩支持 audit/optimize 两种模式，评测样例里达到过 78.81% 压缩率；防幻觉体系有五层面试摘要版、十四层工程展开版；渐进式工具披露防止工具滥用，多层安全防护覆盖注入检测、输出脱敏、操作审批、限流熔断。这个过程让我理解了怎么把 LLM Demo 变成生产可用的系统。"

#### ⭐ STAR 法则版（结构化面试回答）

> **Situation：** 运维团队排障需要在 4+ 个系统间切换，信息分散，新人上手慢，凌晨排障容易漏步骤。
>
> **Task：** 设计一个智能运维助手，用自然语言统一排障入口，自动查指标、查日志、查知识库，生成带证据的诊断报告。
>
> **Action：**
> - 架构设计：四层架构（Controller → Service → Agent → Support），Go + Eino + DeepSeek + Milvus
> - Agent 双引擎：ReAct（简单问答）+ Plan-Execute-Replan（复杂诊断）+ GoS 信念图（结构化收敛）
> - 工程化：上下文压缩（audit/optimize，可用评测样例说明 78.81% 压缩率）、防幻觉体系（五层摘要 / 十四层展开）、渐进式工具披露、多层安全防护
> - 可观测性：全链路 trace、Prometheus 指标、工具健康度收集
>
> **Result：** 系统已跑通完整链路。RAG 历史样例评测口径可讲 Recall@10=78%，但面试时要补充 eval runbook / report 作为证据；上下文压缩样例达到过 78.81% 压缩率，当前配置默认关闭或 audit，是否实际压缩由 `context_compression.mode` 决定。

### 问题 3

**用户发了一条消息 "MySQL 连接池满了怎么办"，这条消息在系统中经历了哪些关键步骤？请按时间顺序说出来。**

<details>
<summary>点击查看参考答案</summary>

1. **Controller 接入：** GoFrame HTTP Server 收到 POST 请求，经过 Auth 认证和 RateLimit 限流。
2. **Service 准备：** MemoryService 检索用户历史记忆，ContextAssembler 装配上下文（注入记忆 + System Prompt + 设定 Token 预算）。
3. **Agent 推理：** ReAct Agent 启动 Think-Act-Observe 循环。
   - Think：LLM 分析需要查什么信息。
   - Act：调用工具（query_metrics 查 MySQL 连接数、query_logs 查错误日志、query_docs 查 MySQL 连接池 SOP）。
   - Observe：分析工具返回结果。
4. **Support 执行：** 工具层调用 Prometheus API、日志平台、Milvus 向量检索。
5. **Agent 生成回答：** LLM 综合所有信息生成诊断建议。
6. **Service 收尾：** 保存对话记忆、记录 Token 消耗。
7. **Controller 返回：** HTTP Response 返回诊断报告给用户。
</details>

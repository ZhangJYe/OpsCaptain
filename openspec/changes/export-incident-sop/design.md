## Context

当前事故视图已经持有 `IncidentSession` 的标题、策略、轮次、事件和结论，并在前端呈现证据与建议动作。见 proposal.md 与 `incident-sop-export` 规格；本次不需要修改事故数据结构或服务端 API。

## Goals / Non-Goals

**Goals:**

- 从当前加载的事故生成结构稳定、适合团队复核的 Markdown SOP 草稿。
- 将事实数据、推断结论与人工复核边界明确区分。
- 在浏览器本地完成导出，不产生额外服务端写入。

**Non-Goals:**

- 不把草稿自动写入知识库、Git 或任何外部系统。
- 不生成或执行自动化修复命令。
- 不将缺失的事故字段伪造成已确认事实。

## Decisions

### 1. 在前端基于当前事故生成 Markdown

导出仅消费当前已加载的事故数据，与事故视图使用同一事实来源。这样无需新增 API 或持久化状态，且导出文件反映用户当前查看的事故。替代方案是后端生成文件；它便于审计但会引入存储、权限与文件清理问题，不适合首期本地草稿导出。

### 2. 按“元数据、结论、证据、处置、轮次、复核提示”组织内容

元数据包含事故标识、策略和日期；结论、证据和建议动作分别保留，避免把模型建议混为事实。没有结论时使用明确占位，不补写内容。文件名包含安全化的事故标题与导出日期，便于归档和检索。

### 3. 仅在存在当前事故时显示导出操作

空事故视图没有可导出的事实，因此不展示可操作按钮。导出失败仅提示用户，不影响当前事故或本地视图。

## Risks / Trade-offs

- [浏览器下载被环境拦截] → 保持内容生成独立并显示失败提示，用户仍可从页面复制事故信息。
- [事件内容含不适合 SOP 的噪声] → 只输出有限数量的关键轮次和已投影的证据摘要。
- [结论尚未完成] → 明确标记待补充和待人工复核，不伪造最终根因。

## Migration Plan

1. 增加本地 SOP 生成与下载能力。
2. 在已加载事故的结论区域接入导出操作。
3. 运行前端构建与浏览器下载验证。
4. 回滚时移除导出操作；事故数据与既有诊断流程不受影响。

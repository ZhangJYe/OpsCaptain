## Context

当前前端已通过现有事故列表与详情接口获得 `incidents` 和选中的 `incident`，但“事故记录”界面直接渲染详情组件。见 proposal.md 与 `incident-record-list-detail` 规格；本次不改变后端存储或诊断流程。

## Goals / Non-Goals

**Goals:**

- 将事故记录界面拆分为列表状态与详情状态，并让列表成为默认入口。
- 使一条记录的状态、策略、更新时间与摘要在不进入详情时即可判断。
- 保持详情组件及其中的 SOP 导出基于原有事故数据工作。

**Non-Goals:**

- 不新增筛选、搜索、删除、归档或批量操作。
- 不更改事故创建、SSE 订阅、后端 API 或事故数据结构。

## Decisions

### 1. 将列表与详情作为同一工作区的两个视图状态

由应用层维护“记录列表 / 当前详情”切换；进入“事故记录”时清除当前详情选择并显示列表，选择记录后加载详情。相比把列表常驻在侧栏，主区域列表更适合浏览长标题、摘要与状态，也避免侧栏承担详情导航。

### 2. 列表仅使用已存在的事故摘要字段

列表卡片使用标题、状态、策略、更新时间与 `latest_summary`/最近轮次生成摘要；不在列表内再次请求或生成诊断内容。相比新增后端摘要字段，此方案不增加接口与持久化复杂度。

### 3. 详情保留为已有事故视图，并增加返回入口

详情继续复用现有过程、结论、证据和 SOP 导出；在顶部提供返回列表操作。这样已有的单事故交互无需复制，且返回不修改服务端状态。

## Risks / Trade-offs

- [列表摘要包含较长 Markdown] → 提取首个非空文本并限制为单行，避免列表失去扫描性。
- [正在运行的记录点击后需实时更新] → 继续调用已有详情加载与 SSE 订阅逻辑。
- [从工作台新建事故后用户需要立刻查看] → 创建成功后仍可直接进入该事故详情；手动打开“事故记录”始终回到列表。

## Migration Plan

1. 增加事故记录列表组件与摘要映射。
2. 调整应用导航，使“事故记录”进入列表，选择后加载详情。
3. 在详情增加返回入口，保留 SOP 导出。
4. 验证列表排序、空状态、详情返回与既有事故展示；回滚时恢复原详情入口，不影响后端事故数据。

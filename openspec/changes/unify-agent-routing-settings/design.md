## Context

当前工作台将 Chat/ReAct 与 AIOps 事故入口分开维护：前端仅持久化 AIOps 引擎偏好，设置页仅有 MCP 工具、Skill 和通知。已有统一 Agent 的 `auto` 模式会让完整 ReAct 调用诊断工具，但它是同步入口，且不会为前端创建当前使用的持久化事故。现有事故已持久化 `engine_strategy`，适合作为事故策略锁定的事实来源。参见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 用一个运行配置模型表达“入口方式”与“诊断策略”两个不同层次的选择。
- 用 Flash 的结构化意图识别将自动请求分发到已有的 ReAct 聊天或事故创建入口。
- 保持已创建事故的策略不变，并让工作台始终显示实际使用的策略。
- 在保持现有轻量视觉语言的前提下，让设置页成为可理解的运行控制面。

**Non-Goals:**

- 不把 Flash、ReAct、Plan、GoS 实现为强制的串行多 Agent 流水线。
- 不在本次改造中新增统一 SSE 传输协议；它是后续可选的控制台演进。
- 不新增任意策略编辑、可视化拖拽编排器或运行时修改服务端全局配置的能力。
- 不改变审批边界、工具权限或已有事故历史格式。

## Decisions

### 1. 使用分层运行配置，而不是三选一引擎

前端引入 `AgentRuntimeProfile`：`routeMode` 为 `auto | react | diagnosis`，`diagnosisStrategy` 为 `auto | plan_execute_replan | gos_engine`。选择 ReAct 时不提交诊断策略；选择诊断时可固定策略或允许 Flash 推荐；自动模式同时允许 Flash 判断请求类型和诊断策略。

这使 Flash 的路由职责、ReAct 的对话执行职责与 Plan、GoS 的诊断职责清晰分离。替代方案是把三者平铺为单一枚举；该方案会错误地暗示它们可互换，且无法表达自动模式。

### 2. 将运行配置放在设置页的独立首个分区

设置页新增“运行配置”标签，使用一个主选项组、条件展开的策略卡片和非交互流程预览。主选项组负责入口方式；策略卡片仅在需要时出现；流程预览同步高亮当前路径。顶部栏展示当前的新请求偏好，事故视图展示锁定的实际策略。

替代方案是继续在侧栏放置模式按钮。该方案占用工作区、无法说明策略关系，也不适合作为可持久化配置。

### 3. 将配置存为前端偏好，将策略权限保留在服务端

前端把有效的 `AgentRuntimeProfile` 保存到 localStorage，并在每次新请求中显式传递，不能将其视作服务端全局配置。服务端新增 `agent_router` 下的置信度阈值、默认策略和允许策略配置；前端的本地偏好与 Flash 推荐都不能绕过该白名单。

替代方案是将用户偏好直接写入 `manifest/config/config.yaml`。该方案会错误地把每位用户的 UI 偏好变成部署级配置，且需要重启服务才能切换。

### 4. 新增 Flash 路由决策接口并复用既有执行入口

新增一个轻量路由决策接口。它调用配置的 Flash 模型，要求其输出 `intent`、`recommended_strategy`、`confidence` 和 `reason`，并通过 JSON schema 与白名单进行确定性校验。它不执行工具调用、AIOps 或任何写操作。

前端在自动模式先调用该接口：聊天决策后沿用现有 `/chat_stream`；事故决策后沿用现有事故创建接口并传入固定策略或已校验的推荐策略；待确认决策展示人工选择。显式 ReAct 和固定策略的显式诊断跳过该接口。显式诊断但策略为自动时，只让 Flash 推荐 Plan 或 GoS，不重新判断是否排障。

替代方案是统一 SSE 入口：由一个长连接承载路由、聊天 token、事故创建和诊断事件。它能带来更连续的控制台体验，但需要整合现有 Chat SSE 与事故事件协议、处理重连和去重，不适合首期改造。

### 5. 以事故记录中的实际策略锁定后续轮次

创建事故后，后续追加轮次只读取事故记录的 `engine_strategy`。前端切换运行配置时，只更新下一次新请求的偏好；现有事故的顶部、侧栏和设置页辅助说明均显示“已锁定”。

替代方案是允许每一轮选择策略。该方案会使同一事故的证据和状态机语义混杂，且难以解释最终结论的来源。

### 6. 自动路由采用“缓存、规则、Flash”的三级决策

自动模式先以归一化请求的摘要作为键查询受 TTL 和容量限制的进程内路由缓存；缓存只保存经过校验的 `chat` 或带实际策略的 `incident` 决策。未命中缓存后，按 `agent_router` 配置的高置信故障关键词识别告警、延迟、错误率等明确症状；命中后直接创建事故，固定策略优先于服务端默认策略。只有缓存和规则均未命中时，才调用 Flash 判定意图与建议策略。

缓存键不得保存可读的原始用户输入；待确认、降级和无效结果不得进入缓存。缓存只用于降低分类延迟，不作为事故上下文或路由事实来源，重启后自然失效。

### 7. 工作台负责发起，事故记录负责沉淀

工作台保留唯一输入框，并将所有新请求交给自动路由。顶部和侧栏的新建操作统一回到工作台，不提供“新建事故”快捷入口。事故记录仅用于加载已有事故；没有事故时展示只读空状态。Plan 与 GoS 仅在事故的实际策略、过程与证据视图中呈现。

## Risks / Trade-offs

- [Flash 路由输出不稳定] → 用结构化输出、配置阈值和确定性白名单校验；低置信度或无效输出进入人工确认，不自动执行。
- [客户端旧版本不发送策略偏好] → 服务端采用配置的默认允许策略，保持旧请求兼容。
- [前端偏好与服务端允许策略不同] → 使用服务端返回的实际策略覆盖界面展示，并展示简明原因。
- [新增 API 参数影响兼容性] → 参数保持可选，增加控制器和应用层测试覆盖默认、Plan、GoS 与非法值。

## Migration Plan

1. 在服务端配置中定义 Flash 路由阈值、默认策略和允许策略，并保持当前默认 Plan。
2. 实现只读的 Flash 路由决策接口，补齐结构化输出与参数校验测试。
3. 引入前端运行配置状态和设置页，默认读取当前的 Plan 偏好以保持既有行为。
4. 自动模式根据路由决策调用既有 Chat 或 Incident 入口，浏览器核验策略锁定。
5. 若需回滚，前端隐藏自动路由与路由接口调用，继续使用已有 Chat/AIOps 入口和默认 Plan。

# Agent 评估系统：原理、价值与面试话术

---

## 一、评估系统是什么

一句话：**改代码前后各做一遍同样的题，分数没降就合并，降了就修。**

它不能保证 AI 质量高，只能保证**不会变得更差**。

```
保证质量高 → 优化 prompt、工具、模型
保证不变差 → 评估系统（考试）
两者互补，不是替代。
```

## 二、为什么需要

没有评估系统时：
- 改了代码，觉得"应该没问题"，直接上线
- 用户踩坑了才发现"AI 把内存溢出诊断成了网络问题"

有评估系统时：
- 改完代码跑一遍评估，准确率从 100% 降到 60%
- **上线前就发现问题**，不用等用户投诉

## 三、怎么实现的

### 三层评估

```
第一层：确定性 Gate（CI 自动，秒级）
  - 准备 5 个"标准病例"（题目 + 关键词）
  - 改代码前跑一遍，记录分数（baseline）
  - 改代码后跑同一个题，对比分数
  - 6 项 Gate：准确率、证据覆盖率、延迟、LLM 调用数、降级率、可追溯性
  - 任何一项下降 → 阻断合并

第二层：LLM-as-Judge（手动，分钟级）
  - 用另一个 LLM 给 AI 输出打分
  - 4 个维度：正确性、完整性、连贯性、可操作性（1-5 分）
  - 用于深度分析，不阻断 CI

第三层：deepeval 深度评估（手动，分钟级）
  - Faithfulness：答案是否基于真实证据（防幻觉）
  - Answer Relevancy：答案是否回答了用户问题
  - 用于离线质量审计
```

### 数据流

```
标准病例（eval_cases）
    │
    ├──→ AI 做题 → 实际输出（eval_runs）
    │
    ├──→ Gate 对比 baseline（CI 自动）
    │
    ├──→ LLM Judge 打分（手动）
    │
    └──→ deepeval 深度评估（手动）
```

## 四、面试 Q&A

### Q1: 你怎么保证 AI 输出质量？

> 两层保障：
>
> **第一层是开发时**——优化 prompt、工具调用逻辑、RAG 检索质量。
> 这是提升绝对质量。
>
> **第二层是上线前**——评估系统。每次改完代码，用 5 个标准病例跑一遍，
> 对比改前改后的分数。6 项 Gate 全部通过才能合并。
> 这是防止质量退化。
>
> 两层互补，不替代。

### Q2: 评估系统具体怎么实现的？

> 用 Go 写的，三层：
>
> **第一层是确定性 Gate**，CI 自动跑。准备了 5 个标准病例，
> 每个有"题目 + 期望关键词"。AI 做完题后，用关键词匹配判断对错，
> 算准确率、证据覆盖率等 6 项指标。和 baseline 对比，任何一项下降就阻断 PR。
>
> **第二层是 LLM-as-Judge**，手动跑。用另一个 LLM 给 AI 输出打分，
> 4 个维度：正确性、完整性、连贯性、可操作性，1-5 分。
> 用于深度分析质量问题。
>
> **第三层是 deepeval**，Python 框架，做 Faithfulness 和 Answer Relevancy
> 深度评估。用于离线审计。

### Q3: 评估用例怎么来的？

> 两种来源：
>
> **人工编写**——运维专家根据常见故障场景写标准病例，
> 每个病例包含题目、期望关键词、期望诊断方向。
> 目前有 5 个 holdout case，覆盖 CPU 过载、数据库连接池、
> 网络延迟、Redis 缓存、Kafka 消费积压。
>
> **线上收集**——从真实对话中提取典型案例，人工标注后加入评估集。
> 这样评估集能覆盖真实用户场景。

### Q4: 准确率 78% 是怎么算的？

> 这是 RAG 检索的评估指标，不是 Agent 诊断的。
>
> RAG 评估：准备 18 个测试问题，每个问题标注了对应的正确文档。
> 跑检索，看 Top-10 结果里有没有命中正确文档。
> 命中 14 个 → Recall@10 = 14/18 = 78%。
>
> Agent 诊断评估是另一套：关键词匹配 + LLM 打分。
> 两者分开评估，不混在一起。

### Q5: 评估系统和单元测试有什么区别？

> 单元测试验证**代码逻辑**：函数输入 A，输出是不是 B。
>
> 评估系统验证**AI 质量**：给 AI 一个诊断问题，回答是否正确、完整、可操作。
>
> 区别在于：单元测试是确定性的（同样的输入，同样的输出），
> AI 评估是非确定性的（同样的问题，每次回答可能不同）。
> 所以 AI 评估用"关键词匹配"而不是"精确匹配"，用"Gate 对比"而不是"断言"。

### Q6: 为什么用 Go 写评估系统，不用 Python？

> 项目本身是 Go，评估系统和 Agent 共享类型定义（EvalMetrics、DiagScores），
> 不需要序列化桥接。
>
> Go 的好处：CI 跑得快（秒级），不需要 Python 环境，
> 和主项目一起编译部署。
>
> deepeval（Python）只用于深度离线评估，不进 CI。
> 两套系统通过共享 JSONL 文件通信。

### Q7: 评估用例少（5 个），够吗？

> 不够，但够用了。
>
> 5 个 holdout case 覆盖了 5 类常见故障，是**最小可行评估集**。
> 目的是防止明显退化，不是穷举所有场景。
>
> 生产环境还需要：线上监控（工具调用成功率、诊断准确率）、
> 用户反馈（"这个诊断不对"）、定期人工抽检。
>
> 评估系统是**第一道防线**，不是唯一防线。

### Q8: 评估系统能发现幻觉吗？

> 确定性 Gate 间接发现：如果 AI 说了标准答案里没有的关键词，
> 说明可能在编造。但不能直接判断。
>
> LLM-as-Judge 可以发现：打分 prompt 里明确要求"是否有幻觉"，
> LLM 会检查结论是否基于工具数据。
>
> deepeval 的 Faithfulness 指标直接评估：答案中的每个声明
> 是否能在检索上下文中找到依据。
>
> 三个层次，逐步深入。

### Q9: 这个评估系统有什么局限？

> 三个主要局限：
>
> **第一，覆盖率有限**。5 个 case 不能代表所有场景，
> 可能漏掉某些边界情况。
>
> **第二，关键词匹配粗糙**。AI 说了"数据库连接池满"但关键词是"连接池"，
> 算命中；但 AI 说了"DB pool exhausted"就不算命中。
> 中英文混杂场景会有误判。
>
> **第三，LLM Judge 本身不可靠**。用一个 LLM 评价另一个 LLM，
> Judge 自己也可能犯错。所以 Judge 结果只用于分析，不阻断 CI。
>
> 这些局限可以通过增加评估用例、改进匹配算法、
> 多 Judge 投票等方式逐步缓解。

### Q10: 面试官问"你的项目有什么亮点"？

> 可以讲评估系统：
>
> "我为 AI Agent 建了一套评估体系。每次改完代码，用 5 个标准病例
> 跑回归检查，对比改前改后的 6 项指标，任何一项下降就阻断合并。
> 还有 LLM-as-Judge 做多维度质量评分，deepeval 做 Faithfulness
> 深度评估。这套系统确保 AI 诊断质量不会因为代码改动而退化。"
>
> 面试官大概率会追问细节，你就按上面的 Q&A 回答。
